# Security

## Goal

安全规范的目标是让项目默认更稳，而不是上线后靠事故倒逼补洞。

## Rule

- 参数校验默认开启
- 权限边界明确
- 敏感信息不落日志、不裸返回
- 上传下载接口做类型、大小、权限控制
- 外部回调和后台管理接口重点保护

## Spring Security Boundary

- `SecurityFilterChain` 维护 URL 级粗边界：公开入口、公开只读资源、后台角色大门和登录兜底。
- Controller 的类级或方法级 `@PreAuthorize` 维护具体业务角色，作为动作权限的主要来源。
- 不要在 `SecurityConfig` 复制完整的“HTTP 方法 × URL × 角色”矩阵；重复规则会漂移且难审查。
- matcher 按“公开 → 高权限特例 → 后台总边界 → authenticated”排序，具体规则必须先于通配规则。
- 对携带请求体的高权限写操作，可以保留少量过滤器级前置规则，确保无权请求在参数绑定和校验前返回 403。
- 如果完全依赖方法级权限，必须验证“无权且请求体无效”的请求不会先返回 400；出现该问题时增加最小前置拒绝，不恢复整张 URL 权限表。
- 后台拒绝访问和关键成功操作应保留审计，但审计失败不能覆盖原业务响应。

## Guardrails

- 每个后台 Controller 必须有类级 `@PreAuthorize`，或每个后台 handler 都有方法级 `@PreAuthorize`。
- 对混合公开、商家和后台路由的 Controller，逐方法标注权限，不使用过宽的类级角色。
- 增加静态检查或架构测试，阻止新增后台接口遗漏方法权限。
- 权限回归至少覆盖匿名、普通用户、各后台角色、无效请求体和不存在资源。

## Good Bias

- 认证和鉴权分层清楚
- 管理后台接口默认更谨慎
- 关键操作要保留审计思路
- URL 粗边界与方法级细权限职责清晰，不在两个位置维护同一份细粒度矩阵

## Avoid

- 直接信任前端传参
- 把异常堆栈直接返回给外部
- 在日志里打印 token、密码、手机号等敏感字段
- 只为减少 `requestMatchers` 而改变 401、403、400 的既有安全语义
