# Architecture

## Confirm Architecture

先复用用户、会话或仓库已经明确的架构结论；只有仍无法判断时，才询问是单体还是微服务。

## Monolith

适合：

- 业务边界还比较集中
- 团队不大
- 部署简单
- 服务治理复杂度不值得引入

要求：

- 先选择一种主组织方式，不同时混用“按技术层”和“按业务域”造成双重目录
- 业务边界尚未稳定、团队和部署单元单一时，优先使用扁平技术分层：
  `controller`、`service`、`service.impl`、`manager`、`mapper`、`entity`、`dto`、`vo`、`convert`
- 不要因为未来可能拆微服务，就提前建立 `order`、`payment`、`catalog` 等顶层模块
- 只有领域边界、团队职责或独立演进诉求已经稳定时，才引入业务域子包或 Maven/Gradle 多模块
- 单体到微服务的迁移是独立架构决策，不靠提前复制微服务目录完成
- package 分层和依赖方向必须稳定

## Microservices

适合：

- 多业务域
- 多团队协作
- 独立部署诉求强
- 需要异步解耦或服务治理

要求：

- 服务职责清楚
- 调用链路可观察
- 公共能力边界明确
- 避免过度同步依赖

## Existing Project

- 用户已经明确单体时，不要重复追问，也不要继续按微服务结构改造。
- 先识别现有技术栈和目标边界，再移动 package；不要只改包名而保留越层依赖。
- 结构迁移按“建立目标目录 → 移动顶层类型 → 修复依赖 → 删除旧包 → 门禁验证”的顺序执行。
- 工作树已有改动时，增量修改并保留无关内容，不以重构名义覆盖用户改动。
